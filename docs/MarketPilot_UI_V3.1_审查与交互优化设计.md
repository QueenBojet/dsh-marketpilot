# MarketPilot UI / UX V3.1 审查与交互优化设计

> 适用仓库：`QueenBojet/dsh-marketpilot`，2026-10-09 读取 `main`，Git tree `70631a8bcb191b94865a087d7e661696ec21c4fb`。  
> 运行环境：DeepSeek Harness 原生 Web/Desktop 主面板、Cordis 业务插件、GLM-5.3 max。  
> 状态：**设计与源码静态审查文件，不表示已更改仓库或在 DSH Desktop 中做过实机 GUI 复测。**  
> 依据：用户提交的 `PROJECT_SUMMARY.md`；当前仓库 `src/client/**`、`src/harness/**`；DeepSeek Harness 的 `main` / `sidebar.panellist` 扩展机制。  
> 优先级：P0=本轮必须；P1=下一轮；P2=后续完善。

## 1. 结论与目标

V3.0 已经从右边栏迁移为原生主工作区。根据项目总结，五个阶段已完成，120 项测试和真实 GLM-5.3 关键流程在开发方环境验证。**不要再次做框架级重构。** V3.1 的重点是把“可以调用工具的管理页”转化为“工程师可以持续工作的产品界面”。

目标有四个：

1. **识别成本低**：3 秒内看懂项目当前进度、主要风险、下一步动作。
2. **操作成本低**：每一阶段固定出现「输入→执行→结果→复核→进入下一步」，避免用户猜按钮。
3. **工程信息可信**：需求、证据、参数、型号、人工决策、投标声明可逐项溯源；UNKNOWN 保留清晰状态。
4. **运行状态可靠**：模型可能运行数分钟；执行中的任务、待审批事项、已完成成果不会因为切换页面而失去方向。

产品定位：**专业市场技术工作台**。风格为克制、准确、信息密集而不拥挤的工程 SaaS；不使用游戏化仪表盘、虚假的进度百分比、科技霓虹效果。

## 3. IA：重新组织信息层级，不重新造壳

### 3.1 全局层

DSH 现有左侧栏仍保持原样：聊天会话、工作空间、MarketPilot 入口、设置等。进入 MarketPilot 后，在 `main` 插件主面板展示：

- 顶栏：`MarketPilot` / 当前路径 / 全局搜索（P1） / 模型与任务状态（只读、真实值）。不要重复营造第二套 DSH 应用外壳。
- 顶级视图：**工作台、项目、任务、成果**。项目相关操作尽量在项目内部完成。
- `任务`采用全局视图；项目页只放当前项目的运行状态与待办提示。

### 3.2 项目层

推荐布局：

```text
┌───────────────────────────────────────────────────────────────────────┐
│ MarketPilot   / 我的项目 / CALM 漏油监测      [真实模型/当前运行状态] │
├───────────────────────────────────────────────────────────────────────┤
│ 项目名称                           [状态]  [导入资料] [开始下一步骤]  │
│ 需求：8已确认 / 14总计  · 未决：12 · 当前任务：等待人工审核            │
├───────────────────────────────────────────────────────────────────────┤
│  阶段导航       │ 工作区主体                                    │
│                │                                               │
│  ○ 项目概览     │  ① 输入资料/本轮目标                         │
│  ✓ 需求分析     │  ② 主操作（可点击）                           │
│  ◉ 竞品/政策    │  ③ 结果表格/对比矩阵                         │
│  ○ 证据核验     │  ④ 问题与风险摘要                            │
│  ○ 技术比选     │                                               │
│  ○ 方案编制     │ [底部操作区：上一步 | 保存草稿 | 进入下一步]  │
│  ○ 投标审查     │                                               │
│  ◇ 项目成果     │                                               │
└───────────────────────────────────────────────────────────────────────┘
```

统一阶段导航为**一个纵向步骤导航**。不再在项目页同时显示冗余的上方六阶段胶囊和独立八分区按钮；概览单独展示一张轻量进度总览即可。注意阶段状态 ≠ 页面选择状态，二者继续分别建模。

### 3.3 导航策略

- 打开项目默认定位：第一个待处理阶段；如果有等待人工审核，定位待审核阶段，否则最近使用分区。
- 每一阶段可自由回看，但关键动作必须校验 prerequisites。
- 顶栏面包屑可返回项目列表，切换项目不会丢失当前执行任务。
- 锁定内容说明：不能执行时明确写“需先确认8条客户需求”等具体理由，而不是只有灰色不可点击按钮。

## 4. 视觉规范 V3.1

### 4.1 视觉语言

使用 DSH 正式 UI Primitives 和主题别名 `--dsw-*`。不硬编码光/暗配色，不强行覆盖原生 DSH 标题栏。浅色界面保持中性白灰，关键动作使用 DSH business brand 色；深色采用相同语义角色。

| 元素 | 建议约束 |
|---|---|
| 主工作区最大宽度 | 1440px 左右；密集矩阵页面允许更宽 |
| 项目阶段侧栏 | 200–224px，项目内显示；窄屏转折叠菜单 |
| 内容正文 | 14px 基础，正文/长段 14–15px，二级信息 12–13px |
| 页面标题 | 22–24px；分区标题 16–18px；不使用满屏多层大标题 |
| 标准控件 | H36–40，保持官方 radius/token |
| 表格 | 固定表头、长文本截断、可展开、必要列固定、清晰 hover/focus |
| 任务状态 | 颜色 + 文案 + 图标，不能仅靠颜色 |
| 警示 | 仅危险/待审核处使用；不要全部卡片都加彩色边框 |
| 空状态 | 解释“为何为空/下一步点哪里”，不要展示没有意义的空白 |

### 4.2 CSS 实施方法

当前 `src/client/styles.ts` 通过 `style[data-plugin-css]` 注入样式，是已工作的打包方式。**不要为了 CSS Modules 贸然更换动态客户端 bundle 工艺**：先保持已有注入入口，把各页面样式拆成独立 TS 字符串模块/使用构建期安全合并；如果当前构建能稳定处理 CSS Modules 再择机迁移。遵守 `__ModuleLoader__` 冻结模块表与 bundle 测试约束。

### 4.3 DSH 页面适配

- 原生 `main` + `sidebar.panellist`；不得侵入 `conversation` 主面板。
- 使用官方 `ui-primitives`（以当前真实导出为准）。
- 主工作区滚动容器只能有一层，弹窗/Drawer 自己管理滚动；避免双重纵向滚动条。
- macOS/Windows 桌面框架须留出宿主 chrome clearance。
- 浅色/深色、1440×900、1366×768、1024×768 三种视口必须检查。

## 5. 六阶段具体交互设计

### 阶段 0：项目准备

- 新建项目用一步弹窗：名称（必填）、行业、客户（可匿名）、业务场景（可选）。
- 主操作「导入资料」；标明支持 md/txt，DOCX/PDF 尚未支持并给出转换说明。
- 文档表按角色分类：需求、调研、竞品资料、政策标准、投标文件。上传成功展示文件名、类型、大小、来源状态；不支持文件逐项报错，绝不静默丢弃。

### 阶段 1：客户需求

- 页面首屏展示「已导入资料」「待确认需求」「未决条件」及单个主要 CTA：「分析所选资料」。
- 主表按 `优先级 / 原文 / 标准化表述 / 状态 / 来源 / 操作` 展示。
- 默认将 proposed / conflict / unknown 排在前面；支持按提取批次和状态筛选。
- 选中待确认需求后，底部 sticky action bar：`已选 N 条 | 查看清单 | 提交人工确认`；确认前提供本批摘要与来源。
- **修复 render-phase setState**：结算监听全部迁移至 effect 或受控 query invalidation。
- 人工确认必须使用精确 projectId + runId + batch IDs；经 server Human Gate；不允许自动审批。
- 详情侧板同时显示引用原文、来源位置、标准化文本、澄清问题。P1 再增加按字段编辑需求的真实后端接口。

### 阶段 2：竞品/政策研究

- 页面内顶级双 Tab：竞品、政策与标准；显示目前为**本地资料抽取模式**，联网 Provider 尚未配置，不包装成实时竞品联网研究。
- 竞品页主表：公司/型号/技术方式/关键性能/认证/已核验证据/待补项；参数缺失显示 UNKNOWN。
- 点击产品打开 **厂商信息—参数表—来源片段—关联 Evidence** 侧板；不能只显示 UUID。
- 竞品横向比对 P1：选择2–4产品，点击“加入对比”，在同一矩阵中同单位比较，缺少单位的不自动合并。
- 政策表点击可查看关键条款、版本、发布机构、项目适用性以及来源。不要根据一条摘要暗示标准合规。

### 阶段 3：证据核验

- 默认分“待核验”“已核验”“未知与矛盾”三个视图。
- Evidence 行需同时显示业务结论、证据类型、原文摘要、来源定位、审核状态。
- 点击记录打开 Source Inspector：**主张 → 支撑的原始摘录 → 来源文档/位置 → 关联需求/方案 → 处理方式**。
- **UNKNOWN 绝不默认变 FACT。** 点击应打开核验表单，明确选择：保留 UNKNOWN、转 FACT（必须填写人工依据/关联已核验证据）、转 ASSUMPTION（注明假设与待验证动作）、驳回；后端规则保持/增强，任何转换继续走 Human Gate。
- 对引用模型草稿的声明区分“资料存在”与“资料已核验”，不得仅显示一个模糊绿色标签。

### 阶段 4：技术路线比选

- 首屏横向 2–3 列方案卡：组成、适用场景、优点、限制、工程风险、证据覆盖、UNKNOWN；宽度不足时转标签页。
- 对比矩阵始终可在对比卡下方滚动；行优先展示 MUST 需求，支持只看差异项。
- 选择方案使用明确的整卡选中样式；底部固定“选择理由 + 人工确认”栏。
- 显示决策对后续生成文档的影响；已存在 Decision 时提示新决策会产生版本，不能静默覆盖。

### 阶段 5：技术方案生成

- **方案页面应以文档阅读为中心，不能只在760px侧抽屉中查看15章长文。** 使用三栏：左侧目录（可跳转）/中间 Markdown 阅读区/右侧关键引用与 UNKNOWN（可收起）。
- 方案列表用生成时间/版本标识，默认选取最新合法结果（按 generatedAt/createdAt 降序）；允许回看旧版本。
- 目录必须是真正可以点击并滚动定位的锚点，不再使用无动作 `<span>`。
- 生成前明确展示已确认路线和需求覆盖；未满足时显示阻塞项。
- 正文可复制与预览。P1 才引入逐章修改/重新生成，不应在没有可靠后端版本机制时加入“保存修改”假按钮。
- 未经审核的方案明确标为“草稿/待审核”，不能直接表现为最终交付文件。

### 阶段 6：招投标符合性审查

- 主表：条款号 / 招标原文摘要 / 规范化要求 / 响应状态 / 证据状态 / 风险 / 操作。
- 表头支持“只看未满足/待确认”。
- **必须修复批量选择行为**：选择条款并点击“审查所选 N 条”时只能传 selectedItems；另提供单独“审查全部条款”的明确操作。
- 详情侧板显示条款原文、响应草稿、证据来源、人工修订建议。缺少已核验 FACT/SOURCE 不得打“满足”。
- 若没有可信 Evidence，应显示“待补证”并提供跳转证据台账；不得自动改判。

### 项目成果中心

- 基线、竞品矩阵、路线比选、方案、投标矩阵统一呈现版本、生成时间和审核状态。
- 阅读器显示正文与原文引用，提供 Markdown 下载（经已有的安全导出/人工审核路径），不自动批准。
- 若后端正式导出需要审核，入口必须明确提示审批步骤与保存路径；禁止浏览器绕过受控导出。

## 6. 全局任务中心交互

每个任务卡最少包含：

`项目名称 · 工作流名称 · 状态 · 当前真实步骤 · 耗时/完成时间 · 查看项目 · 取消/重试`。

- 不显示虚假百分比；显示真实 `WorkflowRun.steps`、运行耗时与模型/工具调用统计（有数据才展示）。
- 运行中任务允许离开页面，回到项目仍可看见。
- Server 重启时标“中断、需重试”，不虚称可续跑。
- 查找 Run 时**禁止降级匹配为任意同类型最近 Run**，只允许精确 `runId`；找不到则显示“运行记录不可用”。
- 统一取消动作：运行中可以从当前阶段与全局任务中心取消；等待人审批则显示真正的 Human Gate。
- 完成后用稳定的 `durationMs`，不要继续增加停止任务的计时器。

## 7. 首批代码修复包（UI-R1）

在美术优化前先修复四项高风险交互：

1. `RequirementsPage.tsx` render 中状态修改转移到 `useEffect`，用 `callId/status` 去重。
2. `TenderPage.tsx` 的所选条款审查语义一致，取消选择或零选择时禁用该操作。
3. `SolutionPage.tsx` 默认展示最新方案；目录点击可定位到正确标题；全文阅读不局限窄抽屉。
4. `EvidencePage.tsx` UNKNOWN 核验必须显示显式目标类型和核验理由，不能静默以 FACT 为默认操作。

这四项修改须各有一个 React 交互回归测试（测试不仅断言文案存在，还必须验证提交参数、版本选择、目标 kind 与实际回调）。

| UX-4 方案/投标/成果 | 全文阅读器、可跳转目录、版本选择、条款审查所选项 | 精确审查被选条款、可读15章方案、草稿/审批状态准确 |
| UX-5 任务中心与 E2E | 真实阶段时间线、跨页面运行、错误恢复和截图验收 | CALM 真模型链路、120 项既有测试不回退，补足新增测试 |

每一阶段完成后：`pnpm typecheck`、`pnpm build`、`pnpm test`、检查 Client 冻结导入表；开发机在当前 DSH Desktop 实测点击、截图、控制台错误，并记录未完成项。**真实 GLM-5.3 链路验证只在必要阶段复跑，不必每改一个按钮就耗费数分钟。**

## 9. 安全与工程红线

1. 仅修改 `dsh-marketpilot`；DeepSeek Harness 上游源码作为对照，不更改核心 Agent Loop。
2. 继续复用现有 Cordis Plugin、guarded tools、Project StorageDomain、GLM-5.3 模型路由、Human Gate。
3. Web 客户端不得直接持有模型 API Key；任何工具执行走已存在的受控 API/guarded pipeline。
4. `PROJECT_SUMMARY.md` 说明目前为本地单用户 loopback 部署。若未来远程部署，应独立安全审查 Host 鉴权和 API 用户权限。
5. DSH 桌面鉴权令牌属于敏感信息；自动化测试不得把原始令牌写入测试日志、截图文件名或上传仓库。
6. `fixtures/calm/` 演示数据须标记为“脱敏/合成数据”；不得将离线 Fixture 说成真实联网搜索结果。
7. 不删除原有项目及数据库；变更 Schema 必须先证明旧库兼容或提供可回退迁移。
8. UI 不应替用户完成人工确认或提高证据等级；要强调工程核验边界。
