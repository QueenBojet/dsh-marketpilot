# MarketPilot 比赛演示脚本

> 适用版本：V3.2（2026-10-10，第一阶段 + 第二阶段）
> 演示环境：DSH Desktop + GLM-5.3（zai Provider，max reasoning effort）
> 演示项目：可使用已有的「V3P2 自验收 04:46」或现场新建

## V3.2 演示亮点（对比 V3.0 新增）

- **短编号体系**：全产品以 REQ/EVD/ALT/DEC/TND/DOC/ART-两位序号替代裸 UUID；正式文档尾部附「编号对照」保留完整追溯，数据库主键不变。
- **跨模块跳转**：证据抽屉的需求引用、投标抽屉的证据引用都是可点击短编号，一键落到对应模块并直接打开该记录。
- **任务历史**：任务中心合并持久化运行历史（宿主重启不丢），等待审核置顶，可展开真实步骤。
- **首页聚焦**：继续项目 / 待办审核 / 运行任务三个直达区块。
- **真单栏阅读**：成果与方案阅读器为居中单栏（880px），表格横向滚动，不再有挤在侧栏里的正文。

## 演示前准备（5 分钟）

1. 确认 DSH Desktop 已启动，模型选择 GLM-5.3 / reasoning effort max。
2. 左侧边栏确认「MarketPilot 智策」图标可见。
3. （可选）准备一份 .md 格式的客户需求文件与一份 tender.md。

## 演示流程（约 10 分钟）

### 开场：首页聚焦（1 分钟）

> **说辞**：MarketPilot 是 DeepSeek Harness 的独立业务插件，提供从客户资料到投标方案的完整工作流。首页直接告诉你现在该做什么。

- 点击左侧「MarketPilot 智策」图标 → 首页。
- **「继续项目」卡**：点击直接回到最近项目的工作台。
- 指出「需要处理」待办列表（哪些项目有待人工审核、各几条）与「运行任务」区（暂无则演示空态诚实性）。
- 需要时可切「任务中心」：即使宿主刚重启，**历史运行**依然完整可查（展开一条看真实步骤与耗时）。

### 第一步：项目与资料（1.5 分钟）

> **说辞**：我们通过浏览器直接上传 .md 文件——不需要告诉 AI 文件路径，也不需要在服务器上手动操作。

- 新建项目（输入名称 → 点创建）→ 打开项目。
- 进入「01 资料与需求」→ 拖放或选择 .md 文件上传。
- 指出受控上传的边界：仅 .md/.txt、UTF-8 校验、大小限制。

### 第二步：AI 需求提取（2—4 分钟）

> **说辞**：现在我们让 GLM-5.3 以 max reasoning effort 提取客户需求。界面显示的是真实的模型运行步骤和实际耗时——不是模拟的进度条。

- 勾选文档 → 点「开始需求分析」。
- 展示步骤时间线（读取资料 → 模型提取 → 需求规范化 → 未知项检测 → 保存与待审）。
- 等待完成（约 100 秒）→ 需求表出现。
- **重点**：需求编号列是 **REQ-01、REQ-02… 业务短编号**，不再是 36 位 UUID。
- 指出 UNKNOWN 条目（"最小检出率未冻结""误报率待确认"等）—— **AI 没有编造数据，而是诚实标记了不确定性**。
- 点一条需求的「详情」→ 展示原始表述与来源定位。

### 第三步：人工审核（1 分钟）

> **说辞**：需求确认是人工门——AI 不能代替人做决定。只有我的明确点击才会更新状态。

- 全选待审核 → 点「确认所选需求」→ 弹出审核对话框。
- 检查问题与详情 → 点「确认」。
- 需求变为"已确认"，出现"需求基线已生成"提示。

### 第四步：技术路线（2 分钟）

> **说辞**：系统根据已确认需求生成候选方案，并以矩阵展示每条需求的覆盖程度。

- 进入「04 技术路线」→ 点「生成候选路线」（约 30 秒）。
- 展示 3 张候选卡片：默认摘要两行截断，**点卡片底部「展开」**看完整组成/优势/限制/风险——展开不会误选路线。
- 展示**需求覆盖矩阵**：绿色=完全覆盖，琥珀=部分覆盖；矩阵中的需求同样是短编号。
- 选择一条路线 + 填写理由 → 「提交路线决策」→ 人工门确认（决策条在页面末尾，不遮挡正文）。

### 第五步：方案生成（2 分钟）

> **说辞**：确认路线后，AI 生成完整技术方案。方案开头是「方案摘要」，结尾附「编号对照」——可读性与可追溯性同时成立。

- 进入「05 方案生成」→ 点「生成技术方案」（约 90 秒）。
- 点「预览」→ 单栏阅读器：方案摘要（人工 Decision / 选定路线 / 覆盖率 / 未决 UNKNOWN 计数）→ 需求目标 → 设计边界 → 技术路线 → 分章正文。
- **重点 1**：正文引用全部是 REQ/EVD 短编号；展开顶部「编号对照」可回溯任意记录（含 id 前 8 位）。
- **重点 2**：指出"设计边界与待确认条件"章节——AI 不会把未验证参数伪装成承诺。

### 第六步：投标合规与跨模块跳转（2 分钟）

> **说辞**：最后是投标符合性审查。系统强制执行一条规则：没有已核验证据的条款不能标为"满足"。

- 回到「01 资料与需求」上传 tender.md（kind=tender）。
- 进入「06 投标检查」→ 勾选文档 → 「抽取招标条款」（约 10 秒）→ 点「符合性审查」。
- **重点 1**：无证据条款保持"待确认"而非"满足"——证据闸门在起作用。
- **重点 2（跨模块跳转）**：打开一条条款的「详情」→ 证据引用显示 EVD-xx → **点击它** → 界面直接落到「03 证据审查」并打开那条证据的抽屉（含来源定位与编号对照）。
- 在证据抽屉里点 REQ-xx 引用 → 反向跳到「01 资料与需求」并打开对应需求。

### 收尾（30 秒）

> **说辞**：MarketPilot 的核心是证据驱动——每一个结论都有来源，每一个不确定都被标记，每一个关键决策都由人做，而短编号让这一切对人可读。

- 回到项目概览 → 展示阶段条（已完成阶段绿色、当前阶段高亮，与真实运行状态一致）。
- 进入「项目成果」→ 打开 Requirement Baseline.md 预览：单栏阅读 + 编号对照。

## 备用方案

- 模型超时（>10 分钟）：降低 profile 的 modelTimeoutMs 或使用离线演示（`pnpm marketpilot:demo:smoke`）。
- 网络不可用：全部流程在本地完成，仅需 DSH Desktop 已启动。
- 已有演示数据：V3P2 / CALM 项目包含完整全链路结果（需求→路线→方案→投标），可直接展示成果而不必现场运行模型；旧数据中的 UUID 由显示层即时替换为短编号，效果一致。
